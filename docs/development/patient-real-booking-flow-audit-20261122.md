# 患者真实预约主路径：接口盘点、流程草图与数据缺口（2026-11-22）

本文件是本轮实施前的**审查稿**。本轮只做接口、数据和流程盘点，**没有改患者小程序代码，没有改后端/数据库/Word/云端配置，没有上传或发布版本，也没有增加教学数据**。

## 1. 现有真实接口字段

### 1.1 公开门店 `/public/branches`

- 鉴权：公开（`security: []`）。
- 返回：`branch_id`、`name`、`address`、`phone`、`opening_hours`。
- 限制：
  - 没有服务项目列表；
  - 没有门店照片、地图坐标、经纬度；
  - 没有实时可约数量；
  - `address` 是后台文本地址，不能据此自动打开导航。
- 当前患者端 `public-directory.ts` 已读取并使用这五个字段；门店页已有“教学虚拟地址”标识。

### 1.2 公开医生 `/public/doctors`

- 鉴权：公开。
- 查询参数：可带 `branch_id`（当前患者端只传 `limit`，未按门店过滤）。
- 返回：`doctor_id`、`name`、`job_title`、`branches[] { branch_id, branch_name }`。
- 限制：
  - 不返回医生可提供的服务项目；
  - 不返回排班、日期、时段或余量；
  - 不能在客户端用医生名录臆造“谁出诊”。
- 结论：医生名录只能做“可浏览的公开介绍”，不能作为排班数据源。

### 1.3 患者真实预约总览 `/me/booking`

- 鉴权：患者 Bearer，**必须登录/建档**。
- 返回：
  - `schedules[]`：`schedule_id`、`starts_at`、`ends_at`、`branch_id`、`branch_name`、`dentist_id`、`dentist_name`；
  - `services[]`：`item_id`、`name`、`minutes`、`price`；
  - `availability[]`：`schedule_id`、`item_id`、`duration_minutes`、`slots[]`（ISO 时间字符串）；
  - `appointments[]`：本人预约。
- 关键关系：
  - `availability` 是 `schedule_id × item_id` 的候选时段，已经把“医生排班”和“服务项目”关联起来；
  - `schedules` 提供门店、医生和日期；
  - `services` 提供项目名称、参考价和时长；
  - `slots` 只是候选，不预占，提交仍以服务端最终校验为准。
- 限制：
  - 没有每个时段的剩余号量/容量；
  - 没有 `address`/电话；
  - 不能从 `schedules` 推断没有返回的日期；
  - 必须登录才能拿服务/排班关系。
- 这是目前唯一完整的“门店 × 服务 × 医生 × 日期 × 时段”数据源。

### 1.4 公开可约时段 `/public/slots`

- 鉴权：公开。
- 必填参数：`branch_id`、`item_id`、`visit_type`、`from`、`to`；可选 `dentist_id`；一次最多 31 日。
- 返回：`items[]`，每项 `schedule_id`、`starts_at`、`ends_at`、`dentist_id`、`policy_id`。
- 限制：
  - 必须先知道 `item_id`；
  - 不返回门店名称、项目名称、医生姓名；
  - 不返回余量；
  - 必须再与公开医生/服务数据 join 才能展示；
  - 当前没有公开服务列表接口，因此**未登录用户无法自然完成“先选项目再查 slots”**。

### 1.5 相关写接口

- `POST /me/appointments`：`schedule_id`、`item_id`、`starts_at`、`visit_type`（`初诊`/`复诊`）、`purpose`，可选 `followup_plan_id`；需登录。
- `POST /me/appointments/{id}/cancel`、`/reschedule`、`/checkin`、`/me/changes/{id}/response` 等已有页面使用。
- 可约性最终以服务端提交校验为准；409 必须重新读取 availability，不能沿用旧时段。

## 2. 现有教学数据盘点

以下数量来自仓库里的 `deploy/teacher-demo-seed.sql`，是**教学种子生成规则**，不是本轮重新查询线上库的结果。

| 项 | 数量/范围 | 说明 |
| --- | --- | --- |
| 营业门店 | 2 | 云栖门店、滨江门店，均为“教学虚拟地址” |
| 牙医 | 8 | 4 位/门店；均有教学资质 |
| 服务项目 | 11 | 初诊检查、牙周维护、正畸复诊、种植术后复查、洁牙、儿童窝沟封闭、全瓷冠复诊、树脂补牙、拔牙评估、牙周复查、儿牙涂氟 |
| 门店服务关联 | 2 × 11 | `branch_service` 对两店全部启用 |
| 医生服务关联 | 24 对 | 不是每位医生都能做全部 11 项 |
| 已发布排班 | 112 条（推算） | 8 位医生 × 14 天；每店每天按医生生成 |
| 营业区间 | 56 条 | 2 店 × 14 天 × 上午/下午 |
| 排班时间 | **仅 09:00–12:00** | 下午 13:00–17:00 只有营业区间，没有班次 |
| 教学预约 | 8 条 | 每医生一条，当前日期 +2 天 10:00 |
| 预约政策窗口 | 7 天 | `booking_policy.window_days=7` |
| 诊椅 | 8 把 | 4 把/店，不代表排班余量 |

### 数据缺口（必须先由 Codex 确认）

1. **公开服务列表缺失**：`/public/branches` 没有 services，`/public/doctors` 没有 services，`/public/slots` 又要求先给 `item_id`。未登录用户无法自然完成“门店→项目→公开可约”，只能先登录读取 `/me/booking`。
2. **下午无排班**：营业区间到 17:00，但种子只有上午 09:00–12:00 排班；下午必须显示“无排班”，不能显示“已满”。
3. **政策窗口 7 天 vs 排班 14 天**：接口 availability 只返回当前政策允许的候选；不能把 14 天排班全展示为可约。界面日期范围应以返回的 availability 为准。
4. **无余量/容量字段**：不能显示“剩 N 个号”；只能显示服务端是否返回候选时段。
5. **无门店照片/坐标/服务字段**：不能画地图/导航/图片入口；没有照片就使用现有牙齿背景或纯色卡片。
6. **公开 slots 缺名称**：需要 join `doctor_id` 到公开医生；项目名需要 `item_id`，但当前无公开服务列表。
7. **排班与项目关系只存在于 availability**：不能仅按医生名录生成“该医生今天出诊”的卡片。
8. **“已满”语义不精确**：有排班但 0 个 slots 可能是已约满、资源禁用、政策窗口、项目不可约；建议 UI 用“已无可约时段”，不要直接断言“已满”。

## 3. 推荐患者主流程

### Step 0：首页

- 保留“看牙，从一次安心的预约开始”主视觉。
- 只保留一个主按钮：**开始预约**。
- 首页增加 3 步条：`选门店 → 选项目 → 选时段`，不写长段解释。
- 现有真实/演示模式开关继续明显显示；演示入口不进入此流程。

### Step 1：选门店（公开可浏览）

- 门店卡片显示：名称、地址/区域、营业说明、电话（如有）、`选择该门店`。
- 只使用真实字段；没有照片/坐标就不显示照片/导航。
- 教学种子的“教学虚拟地址”明确标注。
- 门店选择状态保存在页面内存，返回上一步保留。
- 未登录用户可以完成这一步。

### Step 2：选服务项目（需要登录）

**接口现实**：没有公开服务列表，`/public/slots` 又必须先有项目 ID。为了让用户不看到伪造项目，此步需要先登录/建档，读取 `/me/booking` 后：

- 从 `schedules` 过滤当前门店；
- 从 `availability` 找该门店排班关联的 `item_id`；
- 与 `services` join，显示项目卡片：名称、参考价、参考时长；
- 只显示在当前门店排班中实际出现过的项目，不从全量服务目录臆造。
- 如果登录后发现该门店没有可约项目，显示空状态，不伪造。

> 如果 Codex 要求必须在未登录时选项目，则必须先新增公开服务接口；这超出“只改患者小程序”的范围，本轮不建议。

### Step 3：看医生排班（日期卡片）

- 先固定 `branch_id + item_id`。
- 从 `/me/booking` 的 `availability` 和 `schedules` 取候选：
  - 按日期（Asia/Shanghai）分组；
  - 依据 `starts_at` 小时区分上午 `<12:00` / 下午 `>=12:00`；
  - 每个时段保留 `schedule_id`、医生、开始/结束、`slot` 值。
- 采用**按日期卡片**而不是横向日程表：
  - 手机宽度下左侧栏会挤压日程；
  - 接口没有 chair/resource 列，日程表会多出空列；
  - 日期卡片更容易表达上午/下午和“无排班”。
- 状态建议：
  - `可约`：该日期有至少一个 slots；
  - `已无可约时段`：有排班但没有 slots；
  - `无排班`：该日期没有任何该门店/项目的 schedule。
- 不显示“剩余 N”“余量”“已满”等无字段支撑的文案。
- 日期范围取 availability 实际出现的日期，不自行生成 14 天。
- 医生姓名来自 schedule；同一天多位医生分成多个可点击时段组。
- 项目筛选使用顶部横向 chips/下拉，不占左侧栏。

### Step 4：选具体时段

- 在日期卡片内按上午/下午展示时段按钮。
- 选中后显示医生、开始–结束、参考时长/价格。
- 选择日期后再选时段的组合状态保留；返回日期步骤保留日期。
- 无 slots 的日期不可点或只展开空状态。

### Step 5：登录/建档（若 Step 2 未登录）

- 由于公开服务缺口，推荐在 Step 2 前登录；如果产品要求首屏可浏览更多，可在 Step 1 后登录。
- 登录返回后恢复 branch；重新拉 `/me/booking`，校验项目/排班仍存在。
- 如项目/日期/时段失效：清除失效选择，提示“排班已更新，请重新选择”，不自动提交。

### Step 6：确认提交

- 展示：门店、项目、医生、日期、时段、参考时长、价格（只作参考，不承诺收费）。
- 初诊/复诊：无复诊计划时 `visit_type=初诊`，purpose 使用中性“患者端自助预约”；有复诊计划时按现有逻辑 `复诊` + plan purpose/id。
- 提交前检查 `submitting`；提交后 409/网络不明时重新读取，不重复提交。
- 成功后显示真实预约编号，并跳转到“我的预约”；失败保留选择供重试，但提示最终可约性以服务端为准。

## 4. 状态保留与失效规则

| 用户动作 | 保留 | 清除 |
| --- | --- | --- |
| 返回日期步骤 | 门店、项目、日期 | 不选中的 slot |
| 返回项目步骤 | 门店 | 项目、日期、时段 |
| 改门店 | 新门店 | 项目、医生、日期、时段 |
| 改项目 | 门店、项目 | 医生、日期、时段 |
| 登录/切账号 | 门店（若仍存在） | 项目、医生、日期、时段、旧 availability |
| 服务端 409/可用性刷新 | 门店、项目 | 旧日期/时段；保留可重新选中的日期范围 |
| 页面隐藏返回 | 当前页面 state | 旧请求结果按 request id/revision 丢弃 |

不把项目/时段写入本地存储；不缓存真实 availability 作为提交依据。

## 5. 页面与文件草图（待批准后实施）

- 复用 `services/booking-api.ts`；新增纯函数解析/分组（可单测）：
  - `availabilityByBranchItem`
  - `datesForBranchItem`
  - `dateStatus`（可约/已无可约/无排班）
  - `morningAfternoon`
- 现有 `real-booking` 保留“我的预约/改约/签到/协调”功能；首页主按钮进入新流程，旧页面保留管理入口。
- 门店页“进入排班”主按钮跳转到新流程并带上 `branch_id`；不再跳到医生名录或演示预约。
- 首页去掉长解释，改成步骤条 + 一个主操作；真实/演示标识持续。
- 不新增后端接口；如果 Codex 要求未登录选项目，则必须另立公开服务接口任务，不在本轮偷偷用假数据。

## 7. 需要 Codex 决策的问题

1. **未登录选项目**：当前公开 API 缺口；是否接受“门店公开，选项目前登录”，还是要求新增公开服务接口（需改后端，超出本轮范围）？
2. **状态文案**：是否接受“已无可约时段”替代“已满”，避免把资源/政策限制误报为约满？
3. **日期范围**：以 availability 实际日期为准，是否足够？是否需要在 UI 显示政策窗口 7 天？
4. **初诊/复诊**：无复诊计划的普通预约是否固定 `初诊`，还是需要在确认页提供选择？现有接口允许 `初诊/复诊`，但无就诊记录时不应让用户自行选择“复诊”伪造历史。
5. **门店页主按钮**：是否直接进入新流程 Step 1/2，还是先保留门店详情？
6. **真实主路径**：是否允许替换首页“真实预约”按钮进入新流程，同时保留 `real-booking` 做“我的预约/改约/签到”？
7. **教学数据**：如果 Codex 认为“显得少”需要补样例，需先批准增量数据方案；本轮不建议新增医生/门店/排班，也不重跑种子。

## 8. 当前结论

- 用户看到“少”的主要原因不是纯数据量，而是：
  1. 公开页没有服务列表接口；
  2. 真实排班必须登录后才从 `/me/booking` 得到；
  3. 现有界面按医生名录/下拉平铺，没有门店→项目→日期→时段的层级；
  4. 种子只有上午班次；
  5. 政策窗口 7 天，日程看起来更短。
- 在**不改后端**的约束下，最稳妥的实现是：门店公开看；登录后从 `/me/booking` 派生项目/日期；用日期卡片呈现上午/下午；绝不从医生名录推断排班。
- 本轮先提交本审查稿，**未实施**。等待 Codex 对上述 7 个决策点确认后再改代码。
