# 患者预约与改约一致性实施约束

2026-10-29，依据当前 PatientBookingService、booking-api.ts 与 V002 实际核对。

## 当前缺口
患者创建和改约未接 IdempotencyService；小程序也未发送稳定请求键。改约直接覆盖 appointment，丢失原时间与医生；请求未携带 expected_version。不能把前台已完成的幂等保护视为患者端也已实现。

## 实施决定
1. 创建和改约分别使用账号+操作+客户端请求键，复用 operation_request；同键异内容409，同键重放仍检查当前身份和本人归属。重放返回目标预约当前视图，不承诺原快照。
2. 改约必须提交 expected_version。新请求锁内检查版本及已确认状态；重放先命中幂等结果，不能因旧版本再次执行。
3. 原预约保留原时间、项目、医生，状态转已改约并填写取消时间、patient操作来源及改约原因；新预约 previous_id 指向原预约。复用现有字段，不另建重复历史表。
4. 原预约退出活动状态、释放资源、新预约竞争号源和资源、关联复诊计划全部同一事务；任何一步失败全部回滚。复诊计划引用应传到新预约，旧预约仍保留历史引用，满足最多一条活动预约索引。
5. 锁顺序必须统一检查创建、改约、前台操作与营业区间变更，不可直接沿用旧代码先锁预约再锁排班而忽略交叉死锁。
6. 小程序成功改约后采用返回的新 appointment_id 并刷新列表，原预约显示已改约；结果不明时保留相同键，不自动重发。更换患者会话必须清除旧请求上下文。
7. 幂等摘要覆盖原预约、版本、目标班次、项目、时间及原因；服务器生成内部 request_key，不能和客户端键混用。

## 必须验证
同键并发仅一份预约；异内容409；改约同键不重复生成后继；不同键旧版本拒绝；资源竞争失败保留原预约与资源；复诊计划仍仅一条活动预约；他人目标404；小程序超时重试保持同键且成功后切换新编号。

## 状态
本文件为实施约束，不代表功能已完成。当前仍需代码、契约、小程序和真实隔离数据库验证；Word待实现稳定后同步。未批准削减现有资格、门店、排班和政策校验要求。


## 2026-10-29 患者改约历史与防重复
改约请求增加必填 expected_version、reason 和 Idempotency-Key。旧预约转为已改约，原时间、医生、项目及原资源历史保留；新预约 previous_id 指向旧单，继承复诊计划、目的、就诊类型及特殊需求。旧单退出活动、释放资源、新单创建、资源竞争和审计在同一事务中，失败整体回滚。同一幂等键重放返回当前 original/replacement，两者从一条SQL取得；新请求旧版本返回409。复诊计划不因改约完成。

本批改约先按ID顺序锁涉及门店、排班，再锁旧预约；仍需统一前台创建、签到与其他写入路径的整体锁协议，不能声称已消除全部跨模块死锁。政策版本校验（原契约policy_id）、完整资格与营业区间等业务校验尚未补齐，不因本次契约对齐而取消需求。小程序未做开发者工具/真机验证；Word另行同步。
