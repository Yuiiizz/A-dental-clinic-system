## User Scenarios & Testing *(mandatory)*

### User Story 1 - 发布可信排班 (Priority: P1)

负责人为营业门店发布合资格医生的出诊安排，明确初复诊、可约服务、预计时长和资源条件。
患者能知道医生在哪家门店、什么时段可约，避免把营业时间当成医生出诊时间。

**Why this priority**: 排班是患者自助预约和前台人工办理的共同基础。

**Independent Test**: 使用两家合成门店、一名跨店医生和不同资源，独立检查发布与公开查询，不需要收费模块。

**Acceptance Scenarios**:

1. **Given** 门店、医生任职资格、服务时长及资源均有效，**When** 负责人发布，**Then** 患者只看到已经发布的可约安排。
2. **Given** 医生已有跨店班次，**When** 新班次重叠或未满足两班较大交通缓冲，**Then** 发布失败并说明冲突，不改动原班次。
3. **Given** 草稿、暂停或已结束班次，**When** 患者查询，**Then** 不作为可新预约时段展示。
4. **Given** 已有确认预约，**When** 修改已发布班次的医生、门店、时段或服务（以暂停旧班次→新建并发布的方式），**Then** 列出受影响预约并进入协调，不悄悄覆盖患者确认的安排。

### User Story 2 - 找到医生并自主约成 (Priority: P1)

患者按门店、服务和医生查询出诊，可收藏熟悉医生，也可打开他人分享的公开医生名片。
确认身份和时段后直接取得预约凭证，无须前台再审批一次。

**Why this priority**: 对应电话询问排班较多、寻找熟悉医生及重复沟通的问题。

**Independent Test**: 使用预置已发布排班，分别以新患者和已有档案患者完成预约，核对患者与员工看到同一结果。

**Acceptance Scenarios**:

1. **Given** 未登录，**When** 查看门店及医生，**Then** 可查看公开信息；提交预约前必须认证并绑定本人档案。
2. **Given** 新患者已认证，**When** 建立本人档案，**Then** 可继续预约；历史患者须另核验，不凭共享手机号自动认领旧档。
3. **Given** 服务、资格、本人和资源均符合规则，**When** 提交，**Then** 直接确认并显示门店地址、医生、起止时间和取消规则。
4. **Given** 仅剩一个可用安排，**When** 两名患者同时提交，**Then** 最多一人成功，失败者不留下有效占用。
5. **Given** 已成功提交但页面未收到结果，**When** 重试同一请求，**Then** 返回原结果，不新增预约。
6. **Given** 收藏来自熟人推荐，**When** 保存或分享医生，**Then** 仅涉及公开医生资料和本人选择，不公开推荐人的健康信息，不保证该医生始终有号。
7. **Given** 特殊需求需人工核实，**When** 提交申请，**Then** 显示待确认和联系途径，不把申请当成已占号。

### User Story 3 - 取消和改约时保留可信安排 (Priority: P1)

患者在尚未开始接诊时调整安排；取消释放资源，改约失败不丢原有有效预约。

**Why this priority**: 避免取消后仍占号、改约丢号及不合理限制患者。

**Independent Test**: 对预置确认预约执行取消、改约及同时签到，核对最终状态和占用。

**Acceptance Scenarios**:

1. **Given** 本人未接诊预约，**When** 取消并说明原因，**Then** 记录发起方和时间，释放占用；已候诊的同时退出队列。
2. **Given** 新时段可用，**When** 改约成功，**Then** 旧预约记已改约、新预约确认并关联旧单，新单不继承签到。
3. **Given** 新时段被占，**When** 改约失败，**Then** 原有效安排不变；若原医生已经停诊，则原单继续明确显示待协调。
4. **Given** 已开始接诊，**When** 请求取消或改约，**Then** 拒绝按预约流程操作，转人工处理实际诊疗情况。
5. **Given** 患者处于限制期，**When** 查询或取消已有预约，**Then** 仍可办理，且保留人工咨询入口。

### User Story 4 - 前台办理与停诊协调 (Priority: P1)

前台为电话、现场或不会使用小程序的患者办理。医生临时有事时，前台联系患者确认替诊或改期。

**Why this priority**: 保留用户实际经历中的人工沟通与替诊确认，照顾不同患者的使用能力。

**Independent Test**: 使用预置患者和排班，以门店前台账号登记电话预约并演练停诊，无须真实短信服务。

**Acceptance Scenarios**:

1. **Given** 前台有本店权限且核实患者，**When** 代办，**Then** 使用同一号源和约束，保留渠道、经办人及确认依据。
2. **Given** 原医生停诊，**When** 停诊生效，**Then** 停止新增，既有受影响预约标为待协调，不自动替换医生或批量取消。
3. **Given** 已发出替诊建议，**When** 患者未答复或拒绝，**Then** 不落实候选预约；通知送达不能作为同意。
4. **Given** 患者已同意方案，**When** 落实时资源已被占，**Then** 不伪称改约成功，保留原单和沟通事实继续协调。
5. **Given** 网络或订阅通知失败，**When** 前台电话联系，**Then** 可记录结果；不自动读取私人微信聊天。

### User Story 5 - 自助签到与前台协助共用候诊 (Priority: P1)

患者在预约门店扫描有效签到码，符合时窗则进入候诊；也可选择前台协助，不重复取号。

**Why this priority**: 减少重复接待手续，但保留前台核验与现场服务。

**Independent Test**: 对预置已确认预约，分别自助、人工及同时签到，核对唯一候诊号。

**Acceptance Scenarios**:

1. **Given** 本人已确认且可执行预约，在正确门店及已公开时窗内，**When** 扫码，**Then** 预约变候诊中并取得该门店当日唯一候诊号。
2. **Given** 已经签到，**When** 前台再次办理或患者重试，**Then** 返回同一候诊号。
3. **Given** 错门店、过期码、已取消、旧改约单或停诊待协调，**When** 自助签到，**Then** 拒绝自动入队并提示前台协助。
4. **Given** 太早或超出签到时窗，**When** 自助签到，**Then** 显示时间规则和人工入口，不直接记未到或罚款。
5. **Given** 已签到后离店取消，**When** 办理，**Then** 退出候诊且不计未到。

### User Story 6 - 核实履约而不是自动处罚 (Priority: P2)

授权人员区分普通取消、临近取消、未到、诊所原因和已签到过号，处理豁免及申诉。

**Why this priority**: 防止把正常调整误判为恶意占号；限制策略必须先批准再启用。

**Independent Test**: 使用合成事件和可控时间，分别测试未启用政策、阈值、豁免和到期，不依赖真实患者。

**Acceptance Scenarios**:

1. **Given** 政策未批准启用，**When** 记录取消或未到，**Then** 可以核实事实但不产生自动预约限制。
2. **Given** 已启用且公开的示例政策，**When** 正好提前24小时取消，**Then** 作为普通取消，不计临近取消。
3. **Given** 从未签到且原预约时段已结束，**When** 人员核实未到，**Then** 同一预约只记录一次有效事件；时段未结束不能先判未到。
4. **Given** 本店事件满足启用政策的阈值，**When** 限制生效，**Then** 只限制本店新的自助预约，人工就医、已有预约查询和取消保留。
5. **Given** 事件获豁免或限制到期，**When** 重新判断，**Then** 撤销不再满足条件的限制，不重复用旧事件触发新限制。

### Edge Cases

- 患者与医生跨门店重叠、跨店交通缓冲、设备停用及周转时间同时参与可用性核验。
- 预约时间采用左闭右开区间；相邻预约是否可接续还取决于资源周转与交通缓冲。
- 页面仍显示可约但提交时停诊或已被占用：以提交时事实为准。
- 取消与签到、取消与开始接诊同时发生：按合法状态顺序串行生效；签到后取消可以都成功，但最终不得遗留有效候诊或占用；开始接诊后取消必须拒绝。
- 特殊申请待确认不占号，不承诺已经获得治疗安排。
- 未成年人和需协助患者走人工核验；不能把陪同人登录身份当成患者。
- 无空档、迟到或急症先转工作人员或专业人员评估，不自动挤占他人时段。
- 规则修改不追溯加重历史预约；跨政策版本事件不未经说明合并处罚。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 仅公开已核验营业门店、可公开医生资料和已发布可约安排；内部资料不得随查询泄露。（故事1、2）
- **FR-002**: 发布必须核验医生资格、本店任职、初复诊、服务时长、资源及跨店冲突；失败不得部分发布。（故事1）
- **FR-003**: 患者认证及本人档案绑定后才可提交；首次建档可办理，旧档采用额外核验，不能只匹配电话。（故事2）
- **FR-004**: 收藏和分享限公开医生信息；记录本人选择来源，不引入推荐佣金或推荐人病历。（故事2）
- **FR-005**: 首期每次预约（自助或前台代办）确认单个明确项目或复诊建议；复杂多项目需求先人工评估、可安排检查评估，暂不实现多项目组合预约，不让患者任意缩短时长。（故事2、4）
- **FR-006**: 确认时重新核验本人、门店、排班、医生、资源、政策及已有预约，成功同时确认安排和占用。（故事2）
- **FR-007**: 同一患者、医生及独占资源的有效安排不得重叠；跨店与周转缓冲不得被人工代办绕过。（故事1、2、4）
- **FR-008**: 同一提交重试返回原结果；相同请求标识内容被更改时拒绝复用，不产生第二笔预约。（故事2）
- **FR-009**: 预约凭证明确门店、医生、日期起止、状态、规则及联系方式；待确认与待协调不得呈现为正常可接诊。（故事2、4）
- **FR-010**: 取消保留原因、发起方及时间，释放资源并退出已有候诊；开始接诊后不可取消预约。（故事3、5）
- **FR-011**: 改约占新放旧整体生效，保留前后关联且不成环；同一原单最多一个成功后继，失败不丢原有效安排。（故事3）
- **FR-012**: 电话、微信登记和现场代办保留渠道、经办人与核实依据，使用共同号源，不设置正常自助预约的前台审批关卡。（故事4）
- **FR-013**: 停诊或资源不可用先停止新增，再逐项协调受影响预约，不覆盖已发生接诊历史；资源恢复须人工核实，不因预计结束时间已过自动恢复可约。（故事4）
- **FR-014**: 变更建议、通知送达、患者答复与最终落实分别记录；候选不提前占位，同意后仍须重新核验。（故事4）
- **FR-015**: 仅本人、预约门店有效签到码、可执行预约及合法时窗可自助签到；异常转人工，不按异常扫码处罚。（故事5）
- **FR-016**: 自助与人工签到共用唯一候诊记录，号码按门店及当日区分；改约新单不继承旧签到。（故事5）
- **FR-017**: 候诊、离店与未到区分；过号与回队留给后续叫号模块，本阶段仅以合成过号状态验证已签到者不能被记未到；已签到不能记未到，未到须过预约结束且人工核实。（故事5、6）
- **FR-018**: 保存预约创建时展示的政策版本；示例限制政策须经批准且公开后启用，首期不收预约费用或自动罚款。（故事6）
- **FR-019**: 履约事件按发生时间统计，重复核实不重复计数；豁免、申诉和撤销保留依据，限制不得跨店滥用。（故事6）
- **FR-020**: 限制只影响新自助预约，不阻止取消、查询、已有安排或人工就医；诊所原因、已签到过号和已核实紧急情况不计入。（故事3、6）
- **FR-021**: 所有查询与操作按角色在对应门店的授权及本人归属判断；直接更换记录编号不得访问他人或其他门店记录。（全部故事）
- **FR-022**: 排班变更、代办、取消、同意、签到、政策启用与复核须记录操作者、发生时间和结果；公开日志不含病历和完整身份资料。（全部故事）
- **FR-023**: 通知失败不撤销已确认预约，也不伪称送达；工作人员可查询待联系事项并记录电话结果。（故事4）
- **FR-024**: 复诊预约不得重复落实同一计划；取消或未到后计划保持可协调，不能仅凭预约完成就认定治疗目标完成。（故事2、3、6）

### 跨场景验收补充

- 对FR-008：同一请求标识但不同医生或时间的重试必须拒绝，原记录不变。
- 对FR-021：患者替换他人预约编号、A店前台访问B店以及“A店前台+B店库管”尝试办理B店预约，均拒绝且不泄露记录；合法本店操作允许。
- 对FR-022：抽查发布、代办、取消、改约同意、签到和政策复核，均能追到操作者和时间；日志不出现完整患者敏感资料。
- 对FR-024：同一复诊建议重复约两笔有效预约时拒绝第二笔；取消后可重新协调，不能自动关闭治疗目标。
- 对FR-015：签到码只能降低误签到和转发风险，不声称绝对证明到店；疑似异常转人工核验。
- 员工停用或权限撤销后，既有登录状态不得继续执行原授权操作；最后管理员保护及初始化授权在技术计划落实。

### Key Entities

- 组织与门店：实际经营主体及就诊地点，控制公开信息与权限范围。
- 员工、医生与门店任职：执业及服务资格和在哪些门店承担职责；角色不是医生继承类型。
- 账号、患者与身份绑定：区分登录身份和实际患者，核实本人后关联。
- 排班、可约服务与停诊区间：医生何时何店可开展何种服务，及明确不可用时间。
- 资源、不可用区间与预约占用：牙椅设备的可用性与实际预留，不把资产价值当成号源。
- 预约、拟做项目与前后改约关联：记录意向和已确认安排，不代表实际治疗已经发生。
- 变更方案与联系记录：保存协调建议、答复及落实，送达和同意分开。
- 政策、履约事件和限制：版本化规则、可复核事实及限定门店和期限的结果。
- 候诊记录：一次预约最多一份，连接签到入口与后续接诊。
- 主治关系、收藏与复诊建议：三者职责不同，收藏或替诊不自动变更主治。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在合成的两门店场景，完成一次发布、查询、预约、取消重约和签到，全程自助正常路径不要求前台批准。
- **SC-002**: 20名合成患者同时争用同一独占时段，最多一人成功；同一请求重复10次仅有一笔确认预约。
- **SC-003**: 20次改约失败演练中原有效安排均保留；停诊原单均明确显示待协调。
- **SC-004**: 自助与人工对同一预约同时签到及重复办理10次，始终仅一份候诊记录。
- **SC-005**: 覆盖本人、他人、同店、跨店及多角色组合的越权验收案例，全部阻止未授权读写。
- **SC-006**: 本规格列出的取消、未到、豁免、到期及通知失败案例全部满足预期；无未批准的自动限制或扣款。
- **SC-007**: 演示网络正常且20名用户同时操作时，至少95%的排班查询在3秒内显示结果或明确失败提示；提交结果未明时可查询原结果。

上述为拟定验收目标，不是调研统计或已通过测试的结论。

## Assumptions

### 第一阶段范围与依赖

- 必须具备最小的门店、人员任职、服务资源配置和角色门店授权能力；不能只做页面而依赖开发人员每次手改数据。
- 收费、发票、病历填写、叫号接诊全过程、库存成本与经营报表后续独立规格实现。**发票（开票）是完整系统的必要功能**：「第一阶段不提供开票接口」仅表示暂缓实现，不代表从项目删除。开票列入后续「收费结算」阶段，关联患者（申请、查询与抬头信息）、门店（开票主体与税号）、账单（待开票金额与状态）、收款（开票与到账核对）及退费（红冲/作废）；该阶段保留患者申请与查询、财务（finance 角色）开票处理及负责人/财务的权限要求。当前任何演示或模拟的账单/开票数据均为合成演示，不表述为真实开票。本阶段的签到为边界；开始接诊状态可用测试夹具验证取消保护，不声称接诊功能已完成。
- 现有复诊建议和主治关系可作为已核实输入，本阶段不新建临床治疗建议。无建议的初诊以检查评估为入口。
- 短信和订阅消息的真实接入受账户配置与患者授权制约；未接通时明确模拟，电话登记仍可使用。
- 现有报告作为模型基线，不强行在第一阶段实现全部60张表。技术计划须记录所用子集及必要的模型补充。

### 需要在实现中配置而非假装调研已确定的规则

- 门店必须配置签到提前窗口和迟到宽限并向患者展示；未配置时关闭自助签到、保留前台核实入口。测试可配置提前30分钟、迟到15分钟，仅作合成测试参数。
- 示例政策为提前24小时普通取消界限、滚动7天内2次经核实临近取消或未到、暂停自助新预约7天，默认不启用。启用需保存批准人、批准时间和生效版本；模型若缺字段在计划中补充。
- 为避免混合规则处罚，第一版只在同店同一启用政策版本内统计。滚动区间采用复核时刻前7天开区间至该复核时刻闭区间，并按事件发生时间筛选；限制从满足阈值的复核时刻起算，已过期窗口不补罚。这是明确的设计补充，不是既往诊所事实。
- 限制期内不开放患者自助改约新时段，仍可取消和联系前台改约；诊所原因由前台协调。此边界避免借改约绕开限制，属于第一版方案。
- 普通临近改约按旧预约释放时刻判断是否产生待核实事件；诊所原因和已签到离店豁免，同一原预约不因取消与改约重复计次。
- 自动限制重新启用或到期不得重复消费已用于触发的旧事件；申诉复核需重新判断并保留原事实。
- 未有实际试用数据，不承诺提高收入的百分比；先以正确排班、有效预约与可追溯协调验收。
